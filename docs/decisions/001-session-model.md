# 001：会话形态采用一进程一会话

- 状态：已接受（2026-11-01，见决策人栏）。
- 日期与关联任务：2026-10-31；[007：mini-agent 第一版技术方案](../design/007-agent-v1.md)。
- 决策人或审批依据：维护者 2026-11-01 指示"开始第一步的开发"，据其批准按本 ADR 建议方案实施；未单独逐条批复。

## 背景

初步目标要求"能多开 session"。需要在两种形态间选择：多个进程各自持有独立会话（文件持久化），或单一进程内部实现多会话管理器（并发、会话切换 UI、内存隔离）。约束：冷启动不超过 100 ms、崩溃互不影响、Linux 终端使用习惯（多标签页/多 tmux pane 天然并行）。

## 备选方案

- 方案 A（一进程一会话）：实现最简单；隔离由操作系统进程边界免费提供（崩溃、内存、取消请求互不影响）；与终端多开习惯一致；代价是共享状态（如全局配置热更新）需另行设计。
- 方案 B（单进程多会话）：会话切换快、可省进程开销；但需要会话路由、并发 I/O、部分失败恢复，复杂度显著上升，与 v1 "mini" 定位冲突。

## 决策

建议方案 A：每个 `mini-agent run` 进程绑定一个 session id；`--session <id>` 恢复既有会话；历史持久化于 `~/.local/share/mini-agent/sessions/<id>.json`，每轮结束原子写（临时文件 + rename）。多开即多进程。session JSON 携带 `schema_version`，加载规则（高版本拒绝、未知可选字段忽略、未知 role 报错）见设计文档 5.5 节，为跨 session 与多 Agent 演进留格式兼容。

引用依据：[references/coding-agents.md](../references/coding-agents.md) 中登记的会话持久化思路为设计参考，**未在线核对**；本决策主要依据项目自身约束，不依赖外部事实。

## 后果

- 收益：进程级隔离满足验收标准 4；持久化格式简单；无并发原语。
- 代价：同一会话不可被两个进程同时打开（v1 检测同 id 锁文件并拒绝，报明确错误）。进程隔离约束运行态，不限未来的管理型子命令（如 session 导出/克隆/fork）。
- 风险：session 文件并发写坏——以原子写 + 0600 权限 + 启动校验缓解。
- 后续验证：并发两进程 + kill 其一的脚本化测试（见设计文档第 8 节）。
