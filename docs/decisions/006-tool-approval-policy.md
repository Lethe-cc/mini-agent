# 006：命令执行默认逐次人工审批（ask），auto 需显式开启

- 状态：提议（2026-11-02，待维护者评审）。
- 日期与关联任务：2026-11-02；[008：mini-agent v2 技术方案](../design/008-mcp-tools.md)。
- 决策人或审批依据：无——AI 起草，未获人工批复。

## 背景

v2 引入内置 `run_bash`（命令执行）与任意 MCP server 工具，模型可驱动以用户权限运行的副作用。mini-agent 无沙箱、无内置权限系统（architecture 既有声明）。MCP 规范 Tools 页对客户端有明确 WARNING：应有 human-in-the-loop、可视化指示与确认。需要在"agent 可用性"与"破坏面"之间定默认策略。

## 备选方案

- 方案 A（默认逐次确认 ask，会话内可按工具名 `a` 免问；`off` 需显式配置）：安全默认与规范对齐；代价是交互摩擦、`ask` 子命令必须重新定义非交互语义。
- 方案 B（allowlist 起步，名单内自动执行）：折中；但首版名单必然由维护者手填，实际是把决策推迟且更隐蔽。
- 方案 C（全自动，靠模型自律）：体验最顺；无沙箱前提下等于把 shell 交给不可信注入面（含 MCP server 提供的工具描述），不可接受。
- 方案 D（不提供 shell，只做只读类内置工具）：最保守；直接违背"命令执行"的原始诉求。

## 决策

建议方案 A：`tool_approval` 默认 `ask`——TUI 内联展示完整命令/参数摘要并等待 y/n/a（拒绝以 error Tool 消息回填模型，不静默）；`allowlist` 为配置项（按工具名精确匹配）；`off`（全自动）仅当 config 显式写出，且状态行常显 `auto-tools` 警示、文档标注建议容器/最小权限运行。`ask` 子命令默认 `--tools off` 保持脚本确定性，确认语义仅适用于 TTY。工具副作用不因回合失败回滚的限制在 UI 明示（008 第 6 节）。

## 后果

- 收益：默认满足规范"人在环"要求；破坏面受控且可审计（审批事件入日志，仅元数据）。
- 代价：长工具链任务交互成本高（`a` 会话级免问缓解）；`ask` 非交互模式能力受限。
- 风险：审批疲劳导致盲按 y——缓解：默认展示命令全文摘要、`?` 展开完整参数。
- 后续验证：pty smoke 覆盖确认流（y/n/a 三路径）与 `off` 警示行（008 第 8 节，未执行）。
