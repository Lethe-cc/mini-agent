## 1. Context 窗口大小的判定

### 1.1 总格局

四家全部是 **目录（catalog）驱动 + 配置覆盖**，**没有任何一家用"发 oversized 请求读拒绝消息"的探测法**。mini-agent 的 `/context probe` 在参考组里没有同类；最接近的"向 provider 要事实"的做法是：

- Codex：`GET /models` 返回**完整 ModelInfo 目录**（含 `context_window`），带 ETag/TTL 磁盘缓存；
- opencode：拉取 models.dev 中央目录（发布版运行时抓活目录，否则用随仓库 bundle 的快照）；
- Pi：静态生成目录为主，**仅 OpenRouter 一路**在目录之上做活元数据覆盖；
- Codewhale：内置"reviewed catalog"（人工核过来源的行），辅以模型名后缀提示。

### 1.2 Codewhale：目录 → 名字后缀 → 兜底常数，且"来历必须诚实"

解析链（`crates/models/src/lib.rs`）：

1. `context_window_for_model` = reviewed catalog（`reviewed_model_limit`，含 snapshot 别名二次解析）→ 失败则 `explicit_context_window_hint`（lib.rs:218-220）。
2. **`_Nk` 名字后缀解析**：`explicit_context_window_hint`（lib.rs:428）从模型名里解析 `<digits>k`（N ∈ 8..=1024，乘 1000），面向自托管/命名带窗口的模型。关键设计：`name_suffix_context_window_hint`（lib.rs:405-425）单独暴露"这个数字来自命名约定"的事实——注释明确"命名约定可能被服务引擎无视，不是关于路由的事实，任何展示这种窗口的界面必须标注 unverified"。
3. 未知模型兜底：`DEFAULT_COMPACTION_TOKEN_THRESHOLD = 102_400`（lib.rs:40-46，注释写明是 128k 的 80%，从 50k 提上来以避免前缀缓存损失）——目录不认识时压缩触发用保守常数，不猜窗口。
4. 已知模型常量化：`LEGACY_DEEPSEEK_CONTEXT_WINDOW_TOKENS=128_000`、`KIMI_CODE_K3_CONTEXT_WINDOW_TOKENS=262_144` 等带来源 URL 和核实日期（lib.rs:15-39），并注明"高配套餐的窗口必须由显式 `provider context_window` 配置或新鲜 provider facts 提供"。
5. 配置覆盖：`config.example.toml:636,745-748` 暴露 route 级 `context_window`（人工封顶/提额），`crates/engine/src/model_profile.rs` 的 `resolved_capability_profile*` 做 override 合成（config > provider cap > catalog，model_profile.rs:209-245,319-361）。

**错误报文的角色**：Codewhale 解析 provider 错误/stop reason（`is_output_limit_stop_reason`、`model_context_window_exceeded`，models/src/lib.rs:106-180），但用途是**判定截断/溢出条件**，不是发现窗口大小。

### 1.3 Codex CLI：目录整体从 provider 拉，窗口带"有效百分比"折扣

1. `ModelInfo`（`codex-rs/protocol/src/openai_models.rs`）：`context_window: Option<i64>`、`max_context_window`（provider 上限）、`effective_context_window_percent`（默认 95，openai_models.rs:413,478-493）。`resolved_context_window()` 取 `context_window.or(max_context_window)`；`usable_context_window()` = 窗口 × percent / 100（:568-583），auto-compact 限另按 90% 封顶。留 5-10% 余量是**协议级设计**，不是运行时估算。
2. 目录来源三层：随二进制 bundle 的 `models.json`（`codex-rs/models-manager/models.json`）→ provider `GET /models` 的完整 ModelsResponse（`codex-rs/codex-api/src/endpoint/models.rs` path="models"，:33,70-90）→ 磁盘缓存 TTL 复验（`models-manager/src/cache.rs:99-107,200-245`，半 TTL 起可后台刷新）。
3. 用户覆盖：`ModelsManagerConfig.model_context_window: Option<i64>`、`model_auto_compact_token_limit`（`models-manager/src/config.rs:6-7`），CLI/config 直接压目录。
4. 未知模型：目录行缺窗口 → `usable_context_window()` 返回 `None`，压缩路径按 `context_window: None` 跳过裁剪（`core/src/compact_remote_history.rs:77-104`），宁可不压不猜值。

### 1.4 opencode：models.dev 中央目录 + 快照兜底 + 输出预算动态化

1. 目录 = models.dev 数据（`packages/core/src/models-dev.ts:5,18,457`）：`limit: { context, input?, output }`。发布构建运行时抓活目录，抓不到用**随仓库提交的快照** `models-dev/snapshot.txt`（:501-513，`script/update-models-snapshot.ts` 定期刷新）；解析失败的行跳过并告警（:225）。
2. `model-resolver.ts:129`：注释明确"Catalog token limits used by Core for context management"——上下文管理（压缩/溢出判定）全部吃目录数字。
3. 输出侧动态预算：`outputLimit(limit, inputTokens, headroom)`（`packages/core/src/session/model-request.ts:91`，generate 请求带 `WINDOW_HEADROOM=0.01`，:58,271）——max_tokens = 目录 output 与"窗口剩余"取配合，压缩摘要另有 floor（`session/compaction.ts:1200-1201`）。
4. 溢出分类：provider 错误分类器含 `"context-overflow"` / `"payload-too-large"`（`packages/ai/src/schema/errors.ts:7`）——错误只用来**分类触发压缩/重试**，不用来学窗口。
5. 自定义/未知模型：本轮未深查其 config 覆盖链（诚实标注：未验证）。

### 1.5 Pi：生成式静态目录 + OpenRouter 单路活覆盖 + 用户 models.json

1. 目录 = `models.generated.ts`（文件头：`auto-generated by catalog/generate.ts`，`npm run generate-models` 再生成，即构建期抓 models.dev 后固化）。`Model` 类型 `contextWindow: number; maxTokens: number` 为**必填**（`packages/ai/src/types.ts:869-870`）。
2. 唯一运行时覆盖：OpenRouter provider（`packages/ai/src/providers/openrouter.ts:55-57`）：`contextWindow = entry.top_provider?.context_length || entry.context_length || model.contextWindow`，`maxTokens` 同理——静态目录打底、网关新鲜数覆盖、再落回目录。这正是 mini-agent v4.2 缓存 caps 的同类物。
3. 用户自定义模型：`packages/coding-agent/src/core/model-config.ts:53-80`——`contextWindow` 可选，**默认 128000**（TypeBox `default: 128000`）；未知模型给保守 128k 而非拒绝工作。faux 测试 provider 同样 128000 兜底（`providers/faux.ts:508`）。
4. 压缩公式（pi-agent-book `book/03-context-engineering.md:222`）：`tokenCount > contextWindow - reserveTokens`——窗口来自目录事实，reserve 固定，无探测。

### 1.6 对照 mini-agent

mini-agent 的 `config.context_window`（权威）> 缓存 caps `context_length`（=/models 元数据，Pi-OpenRouter 同思路）> `/context probe` > 单值显示。差异点：

- **probe 是参考组没有的第五种路线**，但动机真实：DashScope 兼容网关的 `/models` 不带 `context_length`（mini-agent v4.2 实测），目录又覆盖不全。四家的共同底线是"**目录没数就不假装知道**"，mini-agent 的 OutputCap 不入库、Unknown 不入库与之一致。
- 可借鉴的增量：① Codex 的 `effective_context_window_percent`（窗口×95% 做可用量、90% 触发压缩）——mini-agent 目前 ctx% 只有 70/90 显示阈值，没有把折扣写进分母；② opencode 的 `outputLimit = f(窗口, 已用输入)`——mini-agent 发固定 `max_tokens`，长会话尾部可能超窗；③ Codewhale 的"数字来历分级"（catalog 事实 / 名字提示 / 探测值）与 mini-agent `~` 估算标记同谱系，probe 存入 config 后与手工值不再可区分，是已知的信息丢失点（probe 值可加 `probed_` 溯源字段）。

## 2. Reasoning 级别的判定

### 2.1 总格局

四家全部 **catalog 驱动"该模型支持哪些级别"**，再在 provider 协议层做**级别→线格式的映射表**。mini-agent 的"原样透传、服务器是仲裁者"与四家都不同：四家把"支持性"当作目录事实提前判定，mini-agent 把它当作运行时协商。

### 2.2 Codewhale：三态能力 + 层级枚举 + 收据式设计

- `ReasoningEffortTier`（`crates/models/src/reasoning_effort_tier.rs`）：off/minimal/low/medium/high/xhigh/ultra/auto/max，外加两个特殊终态 `ThinkingEnabledGranularityUnavailable`（开了思考但路由不暴露档位——"effective receipt, never a requested setting"）与 `Unavailable`（无核实的推理控制契约）。刻意用枚举而非自由文本，防 Work Graph 活动成为推理内容旁路。
- 能力判定三态：`model_reasoning_capability -> Option<bool>`（models/src/lib.rs:253），**None=未知 ≠ false=不支持**；bool 包装 `model_supports_reasoning` 仅兼容旧 UI 门（未知默认按不支持走保守路径）。
- 目录行 `reasoning: Option<bool>`（config/catalog/reviewed.rs:54），多来源合并用 consensus。

### 2.3 Codex CLI：目录内 preset 表 + 描述文案

- `supported_reasoning_levels: Vec<ReasoningEffortPreset>`（`openai_models.rs:439`），`ReasoningEffortPreset { effort, description }`（:211-216）——**每个模型的支持档位连同 UI 描述文案都在目录里**，另有 `default_reasoning_level`（:438）。
- `ReasoningEffort` 枚举含 minimal/low/medium/high（+新值，:74-155 带 FromStr/serde）。UI 直接渲染目录 preset，不做运行时试探。
- 随 /models 一起下发（endpoint/models.rs 测试样例 :363-364：`default_reasoning_level` + `supported_reasoning_levels` JSON 形态），缓存机制与窗口同源。

### 2.4 opencode：七档统一词汇 + 协议层各表其主 + prompt-cache 感知

- 统一档位：`ReasoningEfforts = ["none","minimal","low","medium","high","xhigh","max"]`（`packages/ai/src/schema/options.ts:194-195`）。
- 协议映射各写各的：openai-chat 直发 `reasoning_effort`（`protocols/openai-chat.ts:229,856`）；anthropic 走 `thinking.budget_tokens` 且有 `fitThinkingBudget`（预算必须 < max_tokens、≥ 最小值，`protocols/anthropic-messages.ts:1051-1056`）；alibaba（DashScope 系）两条线：openai 形态 `thinking_budget` + fit 调整（`protocols/alibaba-chat.ts:55,72-75`）、messages 形态可**省略强制预算**（"Model Studio accepts enabled thinking without Anthropic's mandatory token budget"，`alibaba-messages.ts:27,32`）。
- 独有设计：**effort 变更的 prompt-cache 处理**（`packages/ai/src/effort-updates.ts:1-24`）——顶层 effort 变化会击穿 provider 前缀缓存；支持逐消息更新的协议保持顶层冻结、用 `Message.effort(...)` 标记下沉，其余路由剥除标记；revert/fork 历史可能让最后一个标记与当前请求不一致，代码显式处理三种分叉。mini-agent 未处理这层（换 effort 会静默付缓存重建成本）。

### 2.5 Pi：model.thinkingLevelMap + clamp + compat 嗅探

- 目录字段：`reasoning: boolean` + `thinkingLevelMap?: ThinkingLevelMap`（`types.ts:864-868`）——**per-model 的"pi 档位→线值"映射表**，缺失键用 provider 默认，`null` 显式标记该档不支持。
- 档位集合与钳制：`EXTENDED_THINKING_LEVELS = off/minimal/low/medium/high/xhigh/max`；`getSupportedThinkingLevels`（`models.ts:1260-1270`：xhigh/max 必须映射表显式给出才可用）；`clampThinkingLevel`（:1272-1291）向两侧就近回落。
- 线格式按 provider 分派（`api/openai-completions.ts`）：标准 OpenAI `reasoning_effort`（:162,730）；zai 网关 `thinking:{type:enabled, clear_thinking:false}` + 可选 effort（:866-875）；DashScope 式 `enable_thinking: !!effort`（:879）。**compat 可从 baseUrl 自动嗅探**（types.ts:874-884），另有 `supportsReasoningEffort` 之类能力开关。
- Anthropic 路：`mapThinkingLevelToEffort` + `thinkingEnabled===false` 显式关思考的兼容位（`api/anthropic-messages.ts:936-990,1198`）。

### 2.6 对照 mini-agent

mini-agent：`reasoning_effort` 非空即原样进请求体、400 给提示不自动降级（"config authoritative, silent removal would lie"），SSE 回显三路证据（顶层/choices[0] 两位置、reasoning_content delta、usage.reasoning_tokens）汇成状态栏显示，/models caps 已保留 reasoning 档位/默认/强制（v4.2，OpenRouter 形态）。

- **v4.2 缓存的 reasoning 元数据（levels/default/forced）已经是 Codex preset 表的同构物**，目前只用于档位提示；下一步可做 Pi 式 clamp（用户输入不支持的档位时给"就近可用档"建议而非裸 400）。
- Codewhale 的三态（支持/不支持/未知）值得吸收进状态栏词汇：mini-agent 现显示"on/级别/未证实"，但"网关从未告知支持性"与"网关明确不支持"共用形态。
- opencode 的 effort 变更击穿 prompt cache 问题在 mini-agent 同样存在（DashScope 有 cache，见 probe 报文 `cached_tokens`），换 `/reasoning` 档位后可在状态栏提示"下一次请求前缀缓存将重建"。
- 透传优先的设计与四家目录优先相反，但两者不冲突：mini-agent 无目录时（自建网关）透传+回显是唯一诚实做法，有 caps 时可叠加目录侧预判。

## 3. 结论要点

1. **窗口判定**：目录是绝对主流（内置/中央 models.dev/随二进制 bundle），provider 活元数据只在支持它的通道上用（Codex /models 全目录、OpenRouter、models.dev）；无人用拒绝错误报文做窗口**发现**，错误报文只用于截断/溢出**分类**。mini-agent probe 是合理的差异化路线，与参考组底线一致：拿不到就明说、宁缺毋滥。
2. **窗口之后**：参考组都吃目录数字做**主动压缩**（Codex 95%/90% 折扣、opencode outputLimit 动态预算、pi/Codewhale 阈值触发），mini-agent 目前只显示 ctx% 不压缩——这是与四家共同行为的最大缺口（若未来加压缩，Codex 的 `effective_percent` 模型最简可抄）。
3. **reasoning**：四家全部"目录声明支持集 + 映射表转线格式 + clamp/回退"；mini-agent 的透传+回显是无目录场景的正解，有 caps 场景可补 clamp 与三态显示。
4. 未验证项（诚实标注）：opencode 自定义/未知模型的 config 覆盖链；Codewhale `provider_lake.rs` route facts 的完整生产者链（只见 `patch.context_window` 挂点 :1061）。
