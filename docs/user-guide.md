# 从模板到项目交付：使用者完整手册

这份手册面向准备使用 AI 开发自己项目的人。你不需要一次理解所有模板文件；按阶段完成操作，并检查每阶段的产出即可。

**最终目标不是让 AI 一次性生成整个系统，而是让你能够明确需求、控制范围、分步实现、验证结果，并拿到与代码一致的交付文档。**

## 阅读与命令约定

- 以下命令默认在**新项目的仓库根目录**执行，即能看到 `AGENTS.md`、`project.json`、`scripts/` 的目录。
- 命令使用 `python3`，需要版本不低于 3.11。
- 已使用 Python 虚拟环境时，请用虚拟环境解释器。
- 文中的 `csv-report` 是贯穿示例；请替换为自己的项目。模板**没有预先实现这个示例应用**。
- 示例文件名、模块和质量命令只有在相应代码创建后才可使用，不能因为出现在文档里就视为已经存在。
- 给 AI 的提示词可复制后修改。任何联网、依赖安装、提交、推送、部署仍需按你给出的授权执行。

## C++ 或已确定开发语言：先选对应路径

本模板 0.2 起支持语言配置。C++ 项目优先阅读 [C++ 指南](languages/cpp.md)，其他语言见 [配置入口](languages/README.md)。主要 C++ 目标已按 Linux + GCC/Clang 优化，建议从 C++ 指南使用 `python3` 和对应 Linux presets。完整流程仍适用，第 2 步可以直接选择语言：

```sh
python3 scripts/init_project.py --name my-cpp-project --description "项目目标" --language cpp --dry-run
python3 scripts/init_project.py --name my-cpp-project --description "项目目标" --language cpp
```

选择 cpp 会生成 CMake、CTest、最小库/CLI、编译检查和项目 CI；python/typescript 分别生成自己的骨架。0.3 起新增 [Go](languages/go.md) 和 [Rust](languages/rust.md)，使用 `--language go` 或 `--language rust` 选择。不会自动安装编译器或依赖。已有项目不能重复初始化，应按语言入口中的迁移步骤操作。

以下 CSV 例子仍是需求拆分示例，不限制你使用哪种语言，也不是语言骨架已实现的业务功能。

## 路线图

| 阶段 | 你需要完成的事情 | 主要产出 | 进入下一阶段前确认 |
| --- | --- | --- | --- |
| 1 | 从模板创建自己的仓库 | 独立项目目录 | 没有改动母模板或带入私人文件 |
| 2 | 检查环境并初始化 | 项目元数据 | 基础检查通过 |
| 3 | 验证 AI 入口 | 启动验收记录 | AI 实际读取了正确规则 |
| 4 | 写清项目背景 | 项目目标、范围、约束 | 不再依赖聊天记忆表达关键需求 |
| 5 | 登记参考资料 | 来源索引和阅读边界 | 来源用途、版本及访问状态明确 |
| 6 | 确认架构与里程碑 | 技术选型、架构、任务列表 | 方案已由你确认 |
| 7 | 建立可验证的骨架 | 最小代码、测试、质量命令 | 基础和业务检查能真实运行 |
| 8 | 完成一个功能闭环 | 功能代码与测试 | 满足当前任务验收标准 |
| 9 | 审查与文档交付 | 最终设计、PR、验证证据 | 代码和文档一致 |
| 10 | 发布与后续迭代 | 可复现交付与维护记录 | 部署或分发方式经过验证 |

建议第一次只做一个很小的功能，走通全流程，再扩展项目。

## 第 1 步：创建自己的项目，不直接开发母模板

### 方式 A：从代码平台的模板创建

如果模板已发布为 GitHub Template repository：

1. 在模板页面使用平台提供的创建新仓库入口，通常为 **Use this template**。
2. 选择自己的组织或账号，填写项目名称。
3. 根据数据政策选择可见性；含公司业务信息的项目不要默认公开。
4. 创建后克隆的是**新仓库**，不是母模板仓库。
5. 在编辑器或 AI 工具中打开新仓库根目录。

GitLab 的模板使用方式依实例配置、版本和权限而异；没有模板入口时可采用下面的文件复制方式。不要为使用模板而绕过公司的仓库政策。

### 方式 B：复制干净的模板目录

适合当前只有本地 `ai-project-template/` 的情况：

1. 将其复制到新的独立目录，例如 `~/projects/csv-report`。
2. 确认包含点号开头的模板文件，例如 `.github/`、`.gitignore` 和 `.editorconfig`。
3. 不复制旧 `.git/`、真实 `.env`、`.references/`、`.venv/`、`.pi/`、密钥、日志或其他私人内容。
4. 如果源目录已经初始化过，不要直接修改 `initialized` 来伪装成新模板；获取未初始化的模板副本。
5. 后续所有初始化和业务修改都在新目录进行。

如需版本控制，在确认目录正确后可以手工运行：

```sh
git init
git status --short
```

此时不必立即推送，也不要把敏感文件批量加入 Git。提交步骤见后文。

**本步完成标准：** 新目录与母模板相互独立；根目录存在 `README.md`、`AGENTS.md`、`project.json`、`docs/`、`scripts/`、`tests/`。

## 第 2 步：检查环境并初始化

### 2.1 确认可用的 Python

```sh
python3 --version
python3 scripts/doctor.py
```

需要 Python 3.11+。如果没有解释器，按公司认可的方式安装；模板不会自动安装。

`doctor` 只诊断，不安装依赖、不修改文件、不读取所有外部资料。首次出现“模板未初始化”和“业务质量命令未配置”属于预期提示。

### 2.2 预览初始化

```sh
python3 scripts/init_project.py --name csv-report --description "读取本地 CSV 并生成统计报告" --stack "待选择" --dry-run
```

检查：

- 名称是否正确：只允许小写字母、数字和连接单词的单个短横线，例如 `csv-report`。
- 描述是否准确，是否包含不该写入仓库的敏感信息。
- 技术栈不确定时可明确写“待选择”，不需要让 AI 猜一个。
- 以上 generic 命令的预览只列出 `project.json` 和 `docs/project-context.md`；使用 `--language` 时还会列出所选语言骨架。两种预览均不写文件。

### 2.3 执行初始化

确认后去掉 `--dry-run`：

```sh
python3 scripts/init_project.py --name csv-report --description "读取本地 CSV 并生成统计报告" --stack "待选择"
python3 scripts/check.py --require-initialized
```

初始化填充元数据，但不会替你确认需求、选择架构或安装依赖。

脚本不允许重复初始化。之后项目改名或技术栈确定时，应同步修改 `project.json` 与 `docs/project-context.md`，而不是再次运行初始化。

**本步完成标准：** `initialized` 为 true，名称和目标正确，基础检查通过；仍没有配置业务质量命令时应明确保留该限制。

## 第 3 步：确认 AI 真正读取了项目规则

### 3.1 打开正确的工作区

在 AI 工具中打开新项目根目录，不要只打开 `src/`，也不要把包含几十个项目的父目录作为唯一入口。

新建会话，先问：

```text
请说明本项目的工作规则、项目背景入口和验证命令，并列出依据文件。
只读取和说明，不修改文件，不执行命令，不联网。
```

观察它是否发现 `AGENTS.md` 或对应工具的薄适配文件。有读取日志时检查日志；不要只凭“已加载全部规则”这句话判断成功。

### 3.2 自动发现失败时显式加载

```text
请先读取仓库根目录 AGENTS.md，然后按 docs/ai-onboarding.md 完成启动验收。
列出你实际读取的文件、项目目标、初始化状态、开发与验证命令、仍缺少的信息。
区分已读取的来源和仅登记的 URL。
只检查和说明，不修改文件、不执行代码、不安装依赖、不访问外网。
```

根据客户端官方支持的规则入口检查设置。本模板提供 `AGENTS.md`、`CLAUDE.md` 和 `.github/copilot-instructions.md`，但不保证任意版本客户端都自动使用它们。

### 3.3 保存一次验收结果

可记录在项目 Issue 中：工具名、版本、工作区路径、是否自动发现、额外配置、实际结果与日期。

**本步完成标准：** AI 能准确指出项目背景和验证命令，知道尚未接入业务门禁，不会把列出的外部链接说成已经阅读。

完整标准见 [AI 启动验收](ai-onboarding.md)。

## 第 4 步：把项目想法写成可开发的需求

先完善 [项目背景](project-context.md)。一开始最重要的不是框架，而是以下六项信息：

| 内容 | 需要回答的问题 | CSV 示例 |
| --- | --- | --- |
| 用户 | 谁使用？ | 需要汇总本地数据的分析人员 |
| 输入与输出 | 用户提供什么，拿到什么？ | 输入 CSV，输出行数和指定数值列统计 |
| 本期范围 | 第一版必须做到什么？ | 命令行读取一个文件、校验列名、输出结果 |
| 非目标 | 明确不做什么？ | 不做 Web 界面、账号、云同步、数据库 |
| 约束 | 环境、安全、规模有什么要求？ | 本地运行、不上传文件、约定输入规模 |
| 验收 | 如何客观判断完成？ | 正常数据结果正确，异常输入有清晰错误 |

不要直接写“数据量很大”“速度要快”；应补充可测量规模、时限和测试环境。如果尚不确定，让 AI 提问，不让它把猜测记录为已确认需求。

可使用以下提示词：

```text
我准备开发一个项目。请读取 AGENTS.md 和 docs/project-context.md，先帮我澄清需求。

用户：需要汇总本地 CSV 的分析人员。
目标：输入 CSV，输出总行数及指定数值列的统计结果。
第一版不做：Web 页面、账号、数据库、云服务。
约束：文件只在本机处理，不上传外部服务。

请先提出影响范围、错误处理、兼容性和验收标准的关键问题。
暂不写业务代码、不选择收费服务、不安装依赖。
等我确认答案后，再更新 docs/project-context.md。
```

讨论确认后，让 AI 把结论写入文件，而不是只保留在聊天里。重要约束应只有一个权威位置，其他文档用链接引用。

**本步完成标准：** 目标用户、第一版边界、非目标、关键约束和可测试验收标准已写入项目背景。脚本通过不能替代这一步的人工判断。

## 第 5 步：告诉 AI 参考哪些第三方仓库和文档

### 5.1 每个来源建立一份说明

复制 [参考资料模板](../templates/reference.md) 到 `docs/references/`，例如 `upstream-cli.md`。这只是建议的新文件名，当前模板没有这个业务来源。

必须填写：

1. 来源 URL 或本地位置。
2. 仓库完整 commit SHA、tag，或文档对应产品版本。
3. 借鉴哪些模块、文件或章节。
4. 明确不参考的部分。
5. 什么时候需要读。
6. 已读、未读、无法访问等真实状态。
7. 代码复用许可是否已核实。
8. 本项目与参考项目的差异。

然后在 [参考资料索引](references/README.md) 添加一行。不要只贴一堆链接，要求 AI 自己猜用途。

### 5.2 可复制的配置请求

把以下尖括号字段替换成你自己的真实信息，再发送：

```text
请按 templates/reference.md 登记以下业务参考，并更新 docs/references/README.md。

来源：<仓库或文档 URL>
版本：<明确 tag、commit 或文档版本；不知道时标注待核对>
用途：仅参考命令行参数组织和错误码设计。
重点阅读：<确认过的文件路径或章节>
排除范围：不参考部署、Web 界面和旧依赖配置。
复用方式：默认借鉴设计，不复制代码；许可证未核实前不要复制或改写源码。

本次只登记我提供的信息，不联网、不克隆、不执行第三方脚本。
没有核对的信息明确标为待核对，不补造来源或版本。
```

### 5.3 到任务开始时再读取

登记和读取是两件事。如果希望联网核对，应明确允许的来源与范围：

```text
现在允许只读访问刚才登记的公开来源，核对指定版本及指定文件。
不要执行来源中的脚本、安装依赖、上传本地文件或扩大访问范围。
报告实际阅读范围、适用结论、与本项目的差异和仍无法核实的信息。
```

私有仓库通过公司批准的工具授权访问，不把 token 写进 URL、提示词或文档。不将私有代码发送到未经批准的搜索或摘要服务。

如使用本地副本，可放入被忽略的 `.references/`，记录实际修订；忽略规则不等于文件系统只读权限。

**本步完成标准：** 每个来源都有明确用途、版本或待核对状态、适用范围和访问边界；AI 能区分“项目要求”和“可借鉴方案”。

## 第 6 步：先确认架构与里程碑，再开始大规模编码

### 6.1 请求技术方案，不直接要求完整实现

```text
请基于已确认的项目背景和参考资料，提出第一版技术方案。
先读取现有代码、docs/architecture.md 和适用工作流。

请给出：
1. 一个推荐方案，以及有实际取舍意义的备选方案。
2. 模块职责、目录建议、数据流和外部依赖。
3. 为什么这些依赖是必要的；能不用的依赖不要加入。
4. 测试、构建和发布方式。
5. 风险、未确定问题和需要我审批的事项。
6. 分阶段任务，每项任务都有可验证的验收标准。

本轮只写方案，不安装依赖、不写业务代码，等待我确认。
```

检查是否过度设计。例如一个本地 CSV 工具通常不需要因为“将来可能扩展”就先加入数据库、消息队列和微服务。

### 6.2 将确认结论写入仓库

- 技术栈元数据：同步 `project.json` 和 `docs/project-context.md`。
- 系统结构：更新 `docs/architecture.md`，保留必要的模板工具说明，但明确业务架构。
- 功能设计：复制 [设计模板](../templates/design.md) 到 `docs/design/` 并更新索引。
- 重大取舍：必要时使用 [ADR 模板](../templates/adr.md)。

模板已有 `001-template-core.md`、`002-language-profiles.md`、`003-go-rust-profiles.md` 和 `004-linux-cpp.md`，它们描述模板工具，不是你的业务设计。可保留作为工具说明，业务设计使用下一个未占用编号；不要误把它们当作业务实现证明。

### 6.3 任务拆分示例

对 CSV 示例，可以拆成：

| 任务 | 内容 | 可验证产出 |
| --- | --- | --- |
| T01 | 最小命令行骨架与测试入口 | 帮助信息可运行，最小测试通过 |
| T02 | CSV 解析与输入校验 | 正常输入、空文件、缺列等行为有测试 |
| T03 | 数值统计 | 用固定数据证明计数、总和等结果正确 |
| T04 | 命令行集成与错误提示 | 正常流程和错误退出状态可验证 |
| T05 | 文档、审查与交付 | 使用示例可复现，最终设计匹配代码 |

具体统计规则、空值行为和错误处理由你确认，不是模板替你作出的业务决策。

任务可使用平台 Issue；也可自行创建 `docs/tasks/` 保存从 [任务模板](../templates/task.md) 生成的任务文件。后者是使用约定，不是模板自带的任务执行器。

**本步完成标准：** 架构和依赖选择得到确认，第一项任务足够小，验收标准明确，重要未决问题没有被悄悄写成结论。

## 第 7 步：建立开发骨架和真正的业务质量门禁

### 7.1 先做能运行、能测试的最小骨架

```text
请按已确认方案，只实现 T01：最小项目骨架。
先说明本次会创建或修改的文件，再按授权执行。

要求：
- 遵循技术栈的惯用结构，不强行保留不适用的目录。
- 保留现有模板工具及其测试。
- 新增至少一个真实业务行为测试，不使用永远通过的占位测试。
- 将实际开发、测试和构建命令写入 docs/development.md。
- 将已可运行的业务质量命令接入 project.json。
- 不实现后续功能，不修改已确认架构，不自动提交或推送。
- 若需要安装依赖，先列出包、版本、来源与原因，等待授权。
```

第一次建议人工检查文件清单和依赖清单，再让 AI 执行。

### 7.2 Python 项目可选虚拟环境

如果业务也使用 Python，可以隔离依赖。以下仅为 Python 项目示例：

```sh
python3 -m venv .venv
.venv/bin/python --version
.venv/bin/python scripts/check.py --require-initialized
```

不需要激活脚本。

以后安装已批准的依赖和执行检查时，都使用该虚拟环境解释器。模板不替你选择依赖管理工具，具体锁文件和安装命令应写入开发指南。

业务使用 Node.js、Java、Go 等其他技术栈时，仍保留 Python 作为模板工具运行时，并另行安装对应业务运行时。

### 7.3 配置 `quality_commands`

generic 默认只运行工具测试；语言配置另有最小示例测试，**也不代表你的业务需求已验证**。在 `project.json` 中保留其他字段，审查并完善 `quality_commands`，不要覆盖已有适用门禁。

假设 AI 已建立 `app_tests/`，且业务使用 Python 标准库 unittest，可采用以下片段：

```json
"quality_commands": [
  {
    "name": "business-unit-tests",
    "argv": ["python", "-m", "unittest", "discover", "-s", "app_tests", "-p", "test_*.py", "-v"],
    "timeout_seconds": 300
  }
]
```

这只是 JSON 对象中的字段片段，不能单独替换整个 `project.json`。`app_tests/` 必须先有真实测试。

配置原则：

- 每项命令使用参数数组，不写成一个带空格的字符串。
- 不使用 `&&`、重定向或 shell 变量展开。
- 首参数为 `python` 时，检查器会使用启动自身的同一解释器，方便虚拟环境保持一致。
- 不让质量命令再次调用 `scripts/check.py`，否则会递归。
- 不能拿 `python --version` 这种环境命令充当业务验证。
- 检查实际测试数量和测试内容。某些测试发现命令在找到零个测试时也可能成功，退出码 0 并不足以证明有有效覆盖。
- 按技术栈增加格式检查、Lint、类型检查、构建、集成测试；安全扫描按团队政策配置。
- 新业务目录最好不要混淆 `tests/` 中已有的模板工具测试；如采用统一测试布局，要在文档中说明各自覆盖范围。

### 7.4 启用严格检查

```sh
python3 scripts/check.py --strict-project
```

使用虚拟环境时：

```sh
.venv/bin/python scripts/check.py --strict-project
```

严格模式仅保证已经初始化、至少配置了一项项目命令，并且实际检查通过。它不能自动判断测试是否充分，也不能替你选择正确的质量门禁。

**本步完成标准：** 项目骨架可运行；至少一个真实业务行为被测试；项目命令能在当前环境执行，且开发指南记录了同样的操作方法。

## 第 8 步：按任务逐个实现，不一次放开整个项目

每次只交付一个清楚的任务包，包括：目标、范围、非目标、约束、参考来源、验收标准和授权。

```text
请读取 AGENTS.md，按 workflows/implement-feature.md 完成 T02。
以本任务文件和已确认设计为依据；先阅读相关实现与现有测试。

范围：实现 CSV 读取和已确认的输入校验，不做统计功能或 UI。
参考：只读取任务列出的资料，遵守其中的版本及排除范围。
验收：按任务中列出的正常、空文件、缺列和无效输入规则添加测试。
授权：允许修改相关源码、测试和文档，允许运行已审查的本地检查。
不允许：新增依赖、联网、修改架构、提交、推送或部署；需要时先询问。

完成后报告：
- 修改文件和行为。
- 实际执行的命令、测试数量及结果。
- 未验证事项、与设计的偏差和剩余风险。
- 需要更新的设计文档。
```

验收时重点看三件事：

1. 是否只实现本任务，而不是顺手重构整个仓库。
2. 测试是否真正断言行为，是否覆盖关键失败场景。
3. AI 的“完成”是否有代码和执行结果支撑。

发现问题时，不要简单说“再修一下”，应给出复现步骤、实际结果、期望结果，按 [缺陷修复流程](../workflows/fix-bug.md) 处理。

**本步完成标准：** 当前任务的每条验收标准都有对应证据；未完成项明确保留，不能通过改写需求来掩盖失败。

---

## 第 9 步：独立审查，再核对最终设计文档

### 9.1 发起只读审查

可以新建 AI 会话降低沿用旧假设的风险，但新会话必须重新加载仓库上下文。AI 审查不是人工审批的替代。

```text
请读取 AGENTS.md，按 workflows/review-change.md 审查当前任务相关变更。
本轮只读，不自动修复、不提交、不批准 PR。

重点检查：
- 验收标准是否真正满足。
- 边界、兼容性、安全和异常处理是否有缺陷。
- 测试是否覆盖实际行为，是否存在空测试或误导性通过。
- 第三方参考、许可证和依赖是否符合约定。
- 文档中宣称的能力是否与代码一致。

按严重程度列出问题、文件位置、影响和证据；区分确定问题与疑点。
没有运行的验证必须写未执行。
```

审查范围要明确为当前 diff、PR 或指定文件；没有 Git 时提供实际修改文件清单，不让 AI 猜哪些是本次变更。

### 9.2 形成最终设计，而不是聊天总结

修复确认的问题后：

```text
请按 workflows/finalize-design.md 核对本次功能的最终设计。
以当前代码、配置、测试和真实执行结果为依据，更新已有设计而不是另写一份重复文档。

必须说明：
1. 最终模块、接口、数据流和关键路径。
2. 实际采用的参考来源、版本、借鉴内容及本地差异。
3. 与原始设计的偏差及原因。
4. 每项验收对应的测试位置、实际命令、结果和限制。
5. 未实现、未验证、兼容性及发布风险。

按需更新 docs/design/README.md、docs/architecture.md 和 ADR。
不要把计划写成已实现，不要把 AI 自查标成已获人工批准。
```

### 9.3 文档规模与任务匹配

- 小型修复：PR 记录原因、验证与文档不适用说明。
- 一般功能：简版设计，覆盖目标、范围、方案、接口、参考、验证与限制。
- 跨模块、公开接口、安全或迁移变化：完整设计，必要时补 ADR。

复制到 `docs/` 的模板必须填完或删除占位字段。不要修改占位符检查规则来绕过未完成文档。

**本步完成标准：** 审查问题已处理或明确接受风险；最终设计能帮助没有参与聊天的人理解实际实现和验证边界。

## 第 10 步：将本地验证接入 CI，再提交 PR

### 10.1 配置业务 CI

通用 `.github/workflows/ci.yml` 只准备 Python 环境，显式使用 `--tooling-only`。语言配置会额外生成 `.github/workflows/project.yml` 作为严格项目门禁。generic 项目需新建业务工作流；已有语言工作流也应按实际业务审查和完善：

1. 按技术栈增加运行时。
2. 根据已审查的依赖清单和锁文件安装依赖。
3. 准备测试需要的非敏感配置；不使用生产数据。
4. 将最终检查步骤改为：

```yaml
- name: Run project quality gates
  run: python scripts/check.py --strict-project
```

1. 根据实际支持的平台调整矩阵，不把未支持的平台标成已经兼容。
2. 运行真实远端 CI，检查各项结果，而不是仅看到工作流文件存在。

模板没有 `.gitlab-ci.yml`。使用 GitLab 时，需要创建相应流水线，并调用相同的严格检查命令；不要认为 `.github/` 会自动在 GitLab 运行。

### 10.2 审查后提交

以下命令由使用者手工操作。先确认 Git 工作区和分支符合团队流程：

```sh
git status --short
git diff
```

检查敏感文件、第三方副本、大型生成物和无关修改。随后仅暂存本次已确认文件，可用 `git add -- 路径1 路径2`，不要照抄这两个示意路径。

提交前再检查：

```sh
git diff --cached --stat
git diff --cached
```

确认暂存内容后再提交和推送到自己的仓库，按平台流程发起 PR/MR。模板不会替你配置身份、远端或自动执行这些操作。

使用 PR 模板写明：目标、变更、参考与设计、验证证据、剩余风险和回滚方式。受保护分支、required checks 和人工审批需要在平台设置，复制模板不会自动启用。

**本步完成标准：** 本地与 CI 使用一致的项目质量入口；CI 实际通过；PR 信息足够审查；不存在未经授权的敏感内容。

## 第 11 步：完成自己的项目，而不只是完成代码

根据项目性质，你可能需要发布 CLI、构建前端、部署服务或交付内部工具。模板不预设部署平台。

交付前至少检查以下内容：

| 交付物 | 应回答的问题 |
| --- | --- |
| 项目 README | 项目做什么、面向谁、如何安装和使用？ |
| 开发指南 | 新开发者如何准备环境、测试、构建和调试？ |
| 架构与设计 | 模块如何协作，为什么这样设计，已知限制是什么？ |
| 使用示例 | 命令、输入和输出是否按实际代码验证过？ |
| 配置说明 | 哪些变量必填，如何安全提供，是否有无密钥示例？ |
| 验证记录 | 哪些平台、版本、行为被测试，哪些没有？ |
| 发布说明 | 当前版本有哪些能力、变更和兼容性影响？ |
| 运维或分发说明 | 如何部署或安装、诊断失败、升级和回滚？ |
| 授权与许可证 | 是否允许发布、第三方复用义务是否满足？ |

### 将 README 从模板介绍转成业务入口

初始化脚本不会自动重写 README。项目开始有真实能力后，让 AI 将根 README 改为你的业务项目说明，保留到本手册、开发指南和 AI 规则的链接。

不要把模板自身“20 个工具测试通过”的历史记录写成你的业务功能已通过验证。业务验证应记录当前项目的真实测试。

### 做一次干净环境复现

在新的工作目录、干净环境或 CI 中，按照文档从头执行：获取项目、准备运行时、安装锁定依赖、配置非敏感测试变量、运行检查、构建或启动、执行一个用户用例。

如果只有原开发机器能运行，说明交付还不完整。涉及真实部署、资源创建或付费操作，先确认环境、权限、预算和回滚方案。

**本步完成标准：** 一个没有参与开发的人可以根据文档运行项目；业务目标得到验收；已知风险和未实现项清楚披露。

## 第 12 步：下一次任务或新会话如何继续

不要要求 AI 凭聊天记忆继续。保存任务状态和重要结论，再使用以下提示词：

```text
请先读取 AGENTS.md、project.json、项目背景，以及当前任务和相关设计。
当前任务：<Issue、PR 或任务文件路径>
已完成：<简短状态，要求以代码和文件核对>
下一步：<本次具体范围>
本次授权：<可读、可写、可执行和可联网的范围>

先报告你核对到的状态、未决问题及计划。
不要覆盖现有未提交修改，不要把上次聊天中的验证结果当成本次已经执行。
```

每完成一个小任务就重复“实现 → 验证 → 审查 → 文档核对”，不要等整个项目结束才第一次检查。

模板升级属于独立维护工作，见 [模板维护](template-maintenance.md)。不要直接用新版模板覆盖项目自己的背景、参考和设计。

## 常见问题与处理顺序

| 现象 | 常见原因 | 建议处理 |
| --- | --- | --- |
| AI 没读规则 | 工作区根目录不对、工具未支持或未启用入口 | 按第 3 步显式加载并完成验收 |
| AI 说已参考，但给不出依据 | 只看到了 URL，或版本无法访问 | 要求列出实际读取文件/章节及版本；不能访问就标明 |
| `python3` 未找到 | 未安装 Python 或不在 PATH 中 | 按公司认可的方式安装 Python 3.11+ |
| `doctor` 报 Python 版本低 | 运行了旧解释器 | 选择或安装符合要求的解释器；不要降低版本要求来掩盖问题 |
| 提示 already initialized | 脚本防止重复覆盖 | 手工同步项目元数据与背景；新项目使用干净模板 |
| 提示 unresolved template placeholder | 文档模板复制后未填完 | 定位提示文件，填写或删除不适用字段；保留的模板放在 `templates/` |
| 提示 missing link target | 文档移动、文件未创建、相对路径错误 | 按链接所在文件计算相对路径；不要创建空文档假装完成 |
| 严格模式提示没有质量命令 | 只完成了模板初始化 | 接入真实业务测试/构建，再执行严格检查 |
| 检查通过但功能坏了 | 命令覆盖不足、零测试或缺少行为断言 | 检查测试数量、断言和验收映射，补充回归测试 |
| 找不到业务测试依赖 | 运行了解释器或环境不同 | 用同一虚拟环境解释器安装已批准依赖并运行检查 |
| 本地通过、CI 失败 | 运行时、依赖、路径或配置不同 | 对比开发指南与 CI；避免引用本机绝对路径 |
| 质量命令无法执行 | 参数写成字符串、依赖未安装、包装器平台差异 | 检查 argv 数组，在目标平台单独试运行正确命令 |
| AI 开始实现范围外功能 | 任务边界和授权不够明确 | 暂停，要求列出已改内容和恢复建议，由你确认，不自动大范围回退 |
| 最终设计像初始方案 | 未对照实际代码与执行结果 | 重新执行最终设计核对，逐项说明偏差和证据 |

## 最终完成清单

- [ ] 新项目与母模板独立，元数据正确。
- [ ] AI 入口在实际工具中验收过，无法自动加载时有显式入口。
- [ ] 用户、目标、范围、非目标、约束和验收标准明确。
- [ ] 参考资料用途、版本、读取状态和许可边界清楚。
- [ ] 技术方案已确认，任务可独立实现和验证。
- [ ] 存在真实业务测试，测试数量和行为断言经过检查。
- [ ] 严格检查通过，门禁覆盖范围符合项目需求。
- [ ] 必要的 CI、安全检查及人工审查实际执行。
- [ ] 最终设计反映当前代码，不把未实现或未验证写成完成。
- [ ] README、开发、配置、使用和交付说明可复现。
- [ ] 没有提交凭据或未经授权的第三方/私有内容。
- [ ] 发布、回滚、限制和后续工作已说明。

**最重要的工作习惯：你负责确认目标、取舍与授权；AI 协助分析、实现和检查；代码、测试和可追溯文档共同证明完成情况。**
